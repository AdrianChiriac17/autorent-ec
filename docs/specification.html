§ 01Scope and product model

AutoRent is a service-based e-commerce application. The catalog shows car models; under each model the customer sees the real cars in the fleet, each with its own installed features and its own daily rate. The customer rents one of those cars, not “a Logan”.

The flow is: browse the catalog, filter by features and dates, choose a car and an interval, add optional extras, choose a pickup location, and place an order. Stripe Test Mode then confirms the payment and the temporary hold on the car becomes a confirmed reservation.

Vocabulary

TermMeaning
CarBrandManufacturer, for example Dacia or Renault.
CarModelThe catalog product, for example Logan 2024. Holds the seat count and the base price per day.
CarOne real fleet unit of a model, identified by VIN and licence plate.
FeatureDefinitionThe global identity of an installed feature, such as Heated seats or 1.0 TCe. Shared by all models.
CarFeatureA feature offered on one model, with that model's surcharge per day.
CarFeatureAssignmentA feature permanently installed on one specific car.
ExtraOptionAn optional add-on to a rental: child seat, roof box, additional driver, prepaid full tank. Not tied to any car or model.
CartItemOne car plus one rental interval. It has no quantity.
OrderItemThe immutable commercial snapshot of one rented car and period.
ReservationThe single record of a car being occupied: payment hold, confirmed, active, completed, cancelled or expired.

Core rules

  1. One cart item is one physical car and one interval [StartDate, EndDate). There is no quantity field.
  2. A user has at most three cart items. The same model may appear more than once.
  3. Every car belongs to exactly one model, and its installed features must be ones that model offers.
  4. Features fall into four groups: Engine, Transmission, Comfort, Assistance.
  5. A car has at most one engine and one transmission; comfort and assistance features can be combined freely.
  6. Two cars of the same model can have different features, and the same feature can cost differently on different models.
  7. Extras can be added to any rental. There is no extras-per-car compatibility table.
  8. A wishlist entry points to a specific car, not to a model.
  9. Prices, availability and permissions are always computed on the server.
  10. No database transaction stays open while the customer is paying on Stripe.

§ 03Database schema

PostgreSQL 17, 23 tables, frozen at ERD v3. The whole schema exists in the repository as EF Core entities, configurations and one initial migration.

Table names, columns and relationships do not change silently: a change is agreed first, then shipped as entity, configuration, migration and tests in one pull request.

ERD v3

Every table with its columns, types and keys. Scroll inside the frame, or switch to full size to read column names comfortably.

  • 01 Catalog and fleet · 7
  • 02 Users and cart · 4
  • 03 Orders and payments · 7
  • 04 Reservations and reviews · 5

How the tables connect

  • A brand has many models; a model has many cars and many images.
  • A feature definition is priced per model in CarFeatures (unique per model and definition) and installed per car through CarFeatureAssignments.
  • A user has at most one cart; a cart has items; each item points to a car and can carry extras.
  • A user has many orders; an order has items, a pickup location and payments. Each order item can have one reservation.
  • Reservations, maintenance blocks and wishlist entries all point to a specific car.
  • A review belongs to its author, to one completed reservation and to the car model.

Rules the foreign keys cannot express

  1. A car can only be assigned features that belong to its own model.
  2. A car has at most one feature from each exclusive group (engine, transmission).
  3. All definitions in a group agree on UniquePerCar: true for engine and transmission, false for comfort and assistance.
  4. The same car never has two blocking reservations with overlapping intervals.
  5. The three-item cart limit holds even when two requests arrive at the same time.
  6. StartDate < EndDate, money is never negative, ratings are 1 to 5.

Rules 1 to 3 span several tables, so they are validated in application services inside a transaction. The simple ones in rule 6 are also database check constraints.

Storage conventions

  • Money is decimal in C# and numeric(18,2) in PostgreSQL. Never floating point.
  • Instants are UTC, stored as timestamptz.
  • Statuses and pricing types are stored as readable strings.
  • VIN, licence plate, email, order number, booking reference and Stripe identifiers are unique.
  • Orders, payments and reservations are financial history: deleting a parent is restricted, not cascaded.

How a price is calculated

carDailyRate = CarModel.BasePricePerDay
             + SUM(installed CarFeatures.ExtraPricePerDay)

lineTotal    = rentalDays * carDailyRate
             + SUM(per-day ExtraOptions.Price * rentalDays)
             + SUM(fixed ExtraOptions.Price)

orderTotal   = SUM(lineTotal) + PickupLocations.Fee

Rental days follow one documented and tested rule, used by both the API and the interface. At checkout the server recalculates everything from current prices and stores snapshots on the order, its items, their features and their extras, so later price changes never alter a past order.

Left out on purpose

Categories, CarOffers, CarFeatureCategories, PriceLogs, UserAddresses, Contacts, CarAllocations, the ASP.NET Identity tables and any refresh-token table. These appeared in earlier drafts or in the legacy application and are not part of this design.

§ 05Architecture

A modular monolith in four .NET projects, with a React single-page application in front of it.

AutoRent.Domain                  entities and enums, depends on nothing
AutoRent.Application    ───────▶ Domain             business rules, DTOs, service classes
AutoRent.Infrastructure ───────▶ Application + Domain   EF Core, migrations, BCrypt, JWT, Stripe
AutoRent.Api            ───────▶ Application + Infrastructure   controllers, wiring, error handling

The API project is the composition root. Application never references Infrastructure. It does use EF Core abstractions such as DbSet<T> directly; that is an accepted, pragmatic shortcut instead of a repository layer that would only mirror them.

Repository layout

backend/    AutoRent.Api · AutoRent.Application · AutoRent.Domain · AutoRent.Infrastructure
frontend/   React app, one folder per feature under src/features
tests/      AutoRent.UnitTests · AutoRent.IntegrationTests
docs/       this specification, the ERD and the implemented API
OLD/        the legacy ASP.NET MVC + SQLite application, kept for reference only

Path of a request

React ── HTTP JSON ──▶ Controller            route, authorisation, request shape
                      ▶ Application service  business rules
                      ▶ IAutoRentDbContextProvider ▶ IAutoRentDbContext
                      ▶ AutoRentDbContext ▶ PostgreSQL
React ◀── DTO or ProblemDetails ◀── Controller

Example, adding a car to the cart: the controller reads the user from the token and validates the request shape. CartService opens one database context, checks the cart count, the car, the interval and the extras, saves, and returns a DTO. Availability shown in the cart is advisory; it is checked again, atomically, at checkout.

Who owns the database context

Services do not receive a long-lived context. They ask a provider for one, use it for a single business operation, and dispose it.

// Application/Services — the pattern every service follows
public sealed class CarCatalogService(IAutoRentDbContextProvider provider)
{
    public async Task<int> GetActiveCarCountAsync(CancellationToken ct)
    {
        await using IAutoRentDbContext db = await provider.CreateDbContextAsync(ct);
        return await db.Cars.AsNoTracking().CountAsync(c => c.IsActive, ct);
    }
}
  • One atomic business operation uses one context and, when needed, one transaction.
  • A context is never shared between requests or parallel tasks.
  • Only Infrastructure knows the concrete context and the database provider.
  • Read queries use AsNoTracking, filter and project on the server, and always paginate.
  • Every asynchronous call carries a CancellationToken.

Catalog and filters

  • Search by model name, with optional brand, date interval, price range and availability.
  • Feature filters use global definition ids, for example GET /api/v1/cars?featureIds=5,8&startDate=…&endDate=…. A car must have all requested features.
  • Asking for two engines or two transmissions is rejected with 400.
  • Matching cars that are taken still appear, marked isAvailable: false, with selection disabled.
  • A page has at most 24 products, with stable ordering.
  • A search result is never a reservation. Availability is checked again at cart and at checkout.

Responses and errors

Responses are DTOs, never database entities. Lists return pagination metadata. Every failure is an RFC 9457 application/problem+json body with a stable machine-readable code and a traceId; stack traces, SQL and password hashes are never returned.

§ 07Accounts and security

There are two kinds of user: customer and administrator, told apart by Users.IsAdmin. IsAccountActive is a suspension switch.

Passwords and tokens

  • Passwords are hashed with BCrypt and never stored or logged in plain form.
  • Emails are normalised and unique regardless of letter case.
  • Login answers wrong email and wrong password with the same message, and is rate-limited per IP.
  • Access tokens are JWTs that last 30 minutes. The API validates signature, issuer, audience and expiry.
  • The signing key must be at least 32 characters, or the API refuses to start.

Permissions

  • The token carries identity only. Admin rights and suspension are read from the database on every request, so demoting or suspending someone takes effect immediately.
  • Ownership of carts, orders, reservations and wishlists is checked on the server. A user id or admin flag sent by the client is never trusted.
  • An admin cannot remove their own admin rights or suspend themselves.

Transport and secrets

  • Tokens travel in the Authorization: Bearer header, not in cookies, so these endpoints are not exposed to cookie-based CSRF.
  • CORS allows only the known frontend origins.
  • All secrets come from .env or environment variables: database password, JWT key, seed account passwords, Stripe keys. None is committed; the repository is scanned for secrets on every pull request.
  • The legacy application collected ID cards and driving licences. The new design does not collect them.
Known limit

Logging out deletes the token in the browser. A token that was already issued stays valid until it expires, which is why its lifetime is short. Server-side revocation or refresh tokens would need a schema change and are not part of ERD v3.

§ 08Checkout, reservations and payments

Delivered in two phases: first everything up to an unpaid order, then payment and real holds on cars.

Phase one: up to an unpaid order Planned

  1. The customer puts up to three cars in the cart, each with dates and optional extras.
  2. The API validates dates, the car, its features, the extras and the cart limit, and recalculates prices.
  3. The customer chooses a pickup location; the server looks up its fee.
  4. The API creates an order and its items with full price snapshots. Order status is New, payment status Unpaid.
  5. The customer sees the order number and summary.

In this phase an unpaid order does not block a car, and nothing is ever marked paid by the browser.

Phase two: Stripe and holds Later

  1. When payment starts, one transaction checks for conflicts and creates a reservation in PendingPayment with an expiry time. The transaction commits before the customer leaves for Stripe.
  2. The customer pays on Stripe's hosted test checkout.
  3. The webhook is verified: signature, matching order, amount and currency. Each Stripe event id is stored once, so a repeated event changes nothing.
  4. A short transaction moves payment, order and reservation to their confirmed states, if the hold is still valid.
  5. Failed, cancelled or expired checkouts stay unpaid and release the hold. A payment that arrives after expiry is reconciled or refunded, never confirmed blindly.

A PostgreSQL exclusion constraint over car and time range will back the rule that two blocking reservations can never overlap, even under concurrent requests.

Life of a reservation

  • PendingPayment
  • Confirmed
  • Active
  • Completed
  • PendingPayment
  • Expired
  • Confirmed
  • Cancelled

The filled statuses block the car for their interval; a payment hold blocks only until it expires. Reservations is the only occupancy table. Maintenance lives in MaintenanceBlocks because it is not a customer order.

Life of an order

  • New
  • Paid
  • Shipped
  • Delivered
  • Cancelled

These are the statuses the course asks for. For a rental, Shipped means the car was handed to the customer and Delivered means it came back.

§ 09Frontend

A React single-page application, organised by feature: auth, catalog, car details, cart, checkout, orders, wishlist, admin.

features/catalog/
├── api/          typed HTTP functions; views never call fetch directly
├── components/   presentation components for this feature
├── hooks/        state and async orchestration
├── pages/        routed screens
├── types/        request and response types
└── utils/        pure helpers
  • TypeScript strict mode, no any.
  • One HTTP client handles the base URL, the bearer token, JSON and error normalisation.
  • Filters, sorting and pagination live in the URL, so a filtered catalog page can be shared and reloaded.
  • Exclusive feature groups use radio buttons; the others use checkboxes.
  • Every screen has loading, empty, error and disabled states, and works at 360 px.
  • The interface may show an estimated price, but the server's total always wins.
  • Inputs are labelled, focus is visible, everything is reachable from the keyboard.
  • No global state library and no large UI kit; shared controls live in src/components.

Running the project

Five commands after installing the .NET 10 SDK, Node.js 22 and Docker Desktop:

cp .env.example .env                       # then set your own passwords and JWT key
docker compose up -d                       # PostgreSQL 17 on localhost:5432
dotnet run --project backend/AutoRent.Api  # API on :5000, applies migrations and seed
npm --prefix frontend install
npm --prefix frontend run dev              # web app on http://localhost:5173
dotnet test                    # backend: unit and integration
npm --prefix frontend test     # frontend

The development seed creates one admin and two customers, plus 4 brands, 5 models, 10 cars with their features, 4 extras and 3 pickup locations. Startup never deletes data.

Code conventions

  • Controllers are thin: no queries, no business rules.
  • Business rules live in Application services; mappings live in Infrastructure.
  • Nullable reference types and analyzers are on; formatting is enforced by .editorconfig.
  • Small, focused services instead of one service per table.
  • Migrations are named for their intent and never edited once shared.

Git workflow

  • main is protected: changes arrive by pull request, with one approval and green CI.
  • Short-lived branches, squash merges, linear history.
  • Each student commits under their own account.
  • Schema changes are agreed first, then shipped with migration and tests together.
  • Submission commits are tagged P1, P2, P3.
Definition of done

A feature is done when it has a typed API contract, validation and permission checks on the server, tests, predictable error states, updated documentation, and a local demo that needs no secrets and no manual database edits.
